## 1. Overview

Buyers (and public/guests) discover products and suppliers. Everything resolves through **one search engine** and **one result surface**. Search/filter and saved-items were deliberately kept out of Module 2 (Catalogue) and live here.

**New model (1):** `SavedItem`.
**Reused:** `Product`, `Category`, `CategoryAttribute` (M2); `Organisation` (M1). Plus indexes on `Product`.
**Category model gets one new field:** `synonyms: [String]` (for keyword → category matching).

**What M3 delivers:**
- Keyword search with synonym matching + Products/Suppliers toggle
- Faceted filters (standard + dynamic attribute facets)
- AI search (modal → single OpenAI call → answer + results)
- Product listing, product detail, public seller profile, category browse
- Saved items (products + suppliers)
- Sorting, pagination, SEO

## 2. Models

### 2.1 `SavedItem` (only new model — polymorphic)
```js
SavedItem {
  orgId,     // ref Organisation — who saved
  targetType,     // 'product' | 'supplier'
  targetId,       // ref Product OR Organisation
  savedAt, createdAt, updatedAt
}
```
- One model handles both product and supplier saves.
- **Unique index** `(orgId, targetType, targetId)` — blocks duplicate saves.
- Index on `orgId` — fast saved-list.

### 2.2 `Category` — add `synonyms`
```js
Category { …existing…, synonyms: [String] }   // e.g. Pharmaceuticals → [medicine, medicines, pharma, drugs, dawai]
```
Seeded per category. The search index uses **category name + synonyms + product text**.

### 2.3 Indexes on `Product` (no new model)
- Text index on name + description (+ searchable attribute values).
- Filter indexes on `categoryId`, `status`, **`sellerCountry`** (§A23 — Product has no own `country`; this is the denormalised org-country copy), and `attributes.key` / `attributes.value`.

## 3. Search — three types, one engine

### 3.1 Keyword search
- Buyer types text; a **Products | Suppliers** toggle sets the result type (buyer states intent — no GPT here).
- Matches **product text + category names + category synonyms + seller names**.
- **Synonym matching** solves the core problem: buyers type "medicines", not "Pharmaceuticals & Medical". The `synonyms` field maps the word to the category, and its products/suppliers surface.

### 3.2 Faceted filters
- **Standard facets:** category → sub-category, country, price range, MOQ, type (goods/service), verified-only.
- **Dynamic attribute facets:** generated from `CategoryAttribute` where `filterable: true` (e.g. Textiles → GSM range, Material; Pharma → Form, Prescription). Appear when a category is active.
- **Logic:** OR within a group, AND across groups; show counts; real-time update; normalise units so numeric range filters work.

### 3.3 AI search
- A **✨ AI Search** button opens a **modal** with a Products/Suppliers toggle, a natural-language query box, and example prompts.
- On submit → single OpenAI call extracts keywords + filters → the **same engine** runs → results screen shows an **AI answer** + result cards + an "extracted filters" chip row.
- **Guardrails:** validate the JSON against known categories/attributes; fallback to keyword search on failure/timeout; rate-limit; OpenAI only; no embeddings (Phase 2).
- **Guest access (decided 2026-07-30):** AI search is open to guests like the rest of search — rate-limit is **per-user for logged-in callers, per-IP for guests** (an unbounded GPT endpoint is a billing incident; api-endpoints rule B7).
- Full GPT prompt: see the separate `Search.md`, section 11.

### 3.4 The one engine
- **Engine choice (🔴 RESOLVED — Part B: LOCKED to Atlas Search):** Atlas Search (fuzzy, better relevance, built-in facets, already on Atlas). ~~native Mongo text index~~ — not chosen.
- **Sort:** relevance (default), newest, price.
- **Pagination:** page-based or infinite scroll; lazy-load facets on mobile.

## 4. Availability rules (what appears in results)

- Only `status: active` products.
- Exclude taken-down products and products in deactivated categories (cascade).
- Exclude draft / inactive / archived.
- **B7:** all sellers shown regardless of KYC; verification **never filters**. The public projection carries a **`verified` boolean** (derived server-side from `kycStatus`) — raw `kycStatus`/`rejected` is **never** exposed. Frontend renders the tick from `verified`, not `kycStatus`.
- Guests can search; login required only to save.

---

## 5. Saved items

- Buyer saves **products and suppliers** (SavedItem).
- **Availability behaviour:**
  - Temporarily unavailable (inactive/hidden, category deactivated, taken-down) → **stays** in the saved list, shown as "currently unavailable" (may return).
  - Permanently gone (soft-deleted/archived or hard-deleted) → **removed** via cleanup (post-delete hook/cascade) — no dead entries.
- Chat/enquiry is unaffected by soft-delete (the record is preserved).
- **Seller delete logic (🔴 Part A §A5 — supersedes the below):** delete is **always soft** → `status = 'archived'`, with **no** published-vs-draft branching and **no** hard delete. UI shows a single "Delete"; backend always archives.

## 5b. Seller profile — Public vs Private (detailed)

Seller/exporter profile is **public from signup** (B7 — visible before verification, only the verified tick is gated). "Public profile" does NOT mean all data is public. The public endpoint `GET /exporters/:id` returns only a **public projection**; private fields are never serialised to it.

### 5b.1 Public fields (any buyer / guest can see)
| Field | Notes |
|---|---|
| Company / business name | primary identity |
| **Slug** | public URL handle (`/supplier/:slug`) — a card cannot link to the seller page without it (§A6) |
| Logo | brand image |
| Description / about | company blurb |
| Verified tick + since-date | a **`verified` boolean** (derived server-side from `kycStatus`; raw status / `rejected` is **never** exposed) + `verifiedAt`. ✅ M1's `GET /exporters/:id` already returns both `verified` + `verifiedAt`. When M3 builds the **search-result / card seller projection**, it must carry the same two — never raw `kycStatus`. |
| General location | country / city — **not** exact street address |
| **`entityType`** | `business` \| `individual` — is this a registered business or a one-person seller. A trust signal that sits next to the verified tick, and the field that **closes the cancelled "business type"** (§A22.5). Says nothing about *which* documents were filed, so nothing sensitive. ✅ Shipped + whitelisted 2026-07-30 |
| **`establishedYear`** | from `businessProfile.establishedYear`. Public — already returned by the shipped `GET /exporters/:id`; whitelisted here 2026-07-30 |
| Public catalogue | **active products only** (draft/inactive/archived hidden) |
| **`memberSince`** | account age / trust signal ("member since 2024" reads very differently from a brand-new account). **YEAR ONLY** — derived from `createdAt`, **no schema field**; the exact signup second is never published (a public field carries the minimum the UI needs). ✅ Shipped + whitelisted 2026-07-30 |
| Product count | number of live listings — ✅ **SHIPPED with M2 (2026-07-31)** as `productCount`: `countDocuments({ exporterOrgId, status: 'active', 'takedown.isDown': { $ne: true } })` (taken-down excluded, same shape as the D1 cap query) |

> 🚫 **Removed 2026-07-30:** `Business type` and `Main categories / what they deal in` were rows in this table. Both are **cancelled** — `entityType` covers the purpose. Do not re-add them.

### 5b.2 Private / gated fields (never on the public profile)
| Field | Who can see | Why gated |
|---|---|---|
| KYC documents (business ID / personal ID proof) | super admin / employee (verification only) | sensitive identity docs — legal/privacy |
| Owner's personal ID / personal data | admin only | PII protection |
| Direct contact — phone / email | reached only via **enquiry/chat (M4)** | stop scraping, spam, and off-platform leakage |
| Precise registered / street address | seller + admin (unless seller opts to show) | privacy; general city is enough publicly |
| Internal / auth fields (userId, tokenVersion, role, verification notes, audit trail) | system / admin | never client-exposed |
| Financial / account details | seller + admin | sensitive |
| **`website`** | seller + admin — **our verification use only** | **NOT public** (decided 2026-07-30). It was being returned by `GET /exporters/:id` and has been removed. Do not add it back because it "looks harmless" |

### 5b.3 Rules
- The public route returns a **whitelist projection** (only 5b.1 fields) — never a blacklist. New fields default to private unless explicitly added to the public list.
- **Contact is intentionally hidden** — buyers connect through enquiry/chat (Module 4), not by grabbing a phone/email. This protects sellers and keeps activity on-platform.
- Verified tick reflects **status only**; the underlying KYC documents stay admin-only.
- Same projection applies on web and app.

## 5c. Product — Public vs Private (detailed)

When a buyer searches or opens a product, the backend must return only the **public projection** of the product. Internal/moderation/ownership fields are never serialised to the public routes (`GET /public/search`, `GET /public/products/:id`).

### 5c.1 Public fields (any buyer / guest can see)
| Field | Notes |
|---|---|
| name, description | core listing |
| **slug** | public URL handle (`/product/:slug`) — a card cannot link to the product page without it (§A6) |
| images | Cloudinary URLs |
| category / sub-category | with type (goods/service) |
| price | mode (fixed / range / on-request) + min/max + currency |
| MOQ, unit | goods listings |
| trade info | HS code, country of origin, supply ability, lead time, packaging (goods) |
| service info | engagement type, delivery model, team size, timeline (services) |
| attributes | the category-specific specs (key + value) |
| seller (public projection) | company name, logo, verified tick, general location — via the seller's public profile |
| createdAt / listed-since | trust signal |

### 5c.2 Private / never-returned on public routes
| Field | Who can see | Why hidden |
|---|---|---|
| `status` internal states (draft / archived) | seller + admin | drafts/archived must never surface publicly; only `active` is queryable |
| `takedown { isDown, reason, byUserId, at }` | admin only | moderation data — reason/actor must stay internal |
| `exporterOrgId` raw ref + internal owner IDs | system | resolve to public seller profile instead of exposing raw IDs |
| Seller's private fields (KYC docs, direct contact, exact address) | admin / M4 enquiry | see 5b.2 — never inlined into a product |
| Moderation / audit fields, internal flags | admin | not client data |
| Any `deletedAt` / soft-delete markers | system | archived products are excluded, not shown |

### 5c.3 Query-level rules (what the search endpoint filters)
- Return **only `status: active`** products — draft, inactive, archived, taken-down are excluded at the query level (not just hidden in the response).
- Products in **deactivated categories** are excluded (cascade).
- **B7:** all sellers' products are returned regardless of KYC; verification is **never a filter**. The seller's public projection carries a **`verified` boolean** (derived from `kycStatus`), **never** raw `kycStatus`.
- Seller data on a product is the **public seller projection** (5b.1) — never the raw Organisation document.
- Same projection on web and app.

### 5c.4 Rule of thumb
- **Whitelist projection** — the public route returns only the fields listed in 5c.1. Any new product field defaults to private unless explicitly added to the public list. This prevents accidental leakage of moderation/ownership data.

## 7. Backend endpoints

- `GET /public/search` — keyword + filters + sort + page (`q`, `type`, `category`, `price`, `moq`, `country`, `attr.*`, `sort`, `page`).
- `GET /public/facets` — available filters + counts for the current query/category.
- `POST /search/ai` — AI search (`{ query, target }`) → `{ answer, extracted, results }`.
- `GET /public/products/:id` — product detail.
- `GET /exporters/:id` — seller profile + catalogue + tick (shipped M1 route). Returns **only the public projection** (private fields never serialised).

  **Seller profile — PUBLIC vs PRIVATE** (public from signup per B7, but not everything):
  - **PUBLIC (any buyer/guest):** company name, **slug** (`/supplier/:slug` link); logo, description; **`verified` boolean** + `verifiedAt` (the tick — never raw `kycStatus`/`rejected`); general location (country / city — not exact street); **`entityType`** (business/individual); **`establishedYear`**; **`memberSince`** (**year only**, from `createdAt`); public catalogue (active products only); product count *(⚠️ blocked on M2 — see §5b.1)*. *(Business type + main categories: **cancelled 2026-07-30** — `entityType` above is what carries that signal.)*
  - **PRIVATE / GATED (never on the public profile):** KYC documents (business/personal ID — super admin/employee review only); direct contact details (phone/email — reached only via enquiry in M4, to stop scraping/spam); precise street address; **`website`** (our verification use only); all internal/auth fields (userId, tokenVersion, verification notes, etc.).
- `POST /saved` · `DELETE /saved/:id` · `GET /saved` — saved items (🔴 Part A §A13 **reversed**: **buyer-only**, **buyer-account-scoped** via `SavedItem.buyerOrgId`, ownership-checked).

## 10. Flow (end-to-end)

1. Buyer enters via keyword (with toggle), filters, or the AI modal.
2. Keyword → synonym/index resolves to category + products; AI → extracts filters; filters → narrow directly.
3. All hit the one engine (query + filters + sort + paginate).
4. Availability filter applied (active, not-takendown, category active; B7 tick).
5. Results split: product results → detail; supplier results → profile; category browse → filtered listing.
6. Buyer saves items; saved list respects the temporary-vs-permanent rule.
