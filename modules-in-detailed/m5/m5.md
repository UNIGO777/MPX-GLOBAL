# MPX — Module 5: Admin Console

**Status:** planned and locked, 29 July 2026. Not built.
**Surface:** web only. Not in the mobile app.
**Roles:** superadmin sees everything; employees see a permission-filtered subset of the same console.
**Precedence:** where this contradicts an older plan doc, this document wins.

---

## 1. What this module is

The command centre the operator runs the marketplace from. It is **not a new subsystem** — it is a read and aggregate layer over what M1–M4 already store, plus the moderation actions those modules already defined.

**It introduces no new models.** Everything it shows already exists somewhere: `User`, `Organisation`, `AuditLog`, `Category`, `CategoryAttribute`, `Product`, `Inquiry`, `Conversation`, `Message`.

That property is deliberate and was protected during planning — the two items that would have broken it (featured content, and a settings document) were both moved out. If a future change requires storage in M5, that is a signal to re-check whether it belongs here.

## 2. Where the screens come from

M5 looks like a big module. It mostly isn't — most of its screens were specified by other modules and M5 only gives them a home.

| Origin | Screens | State |
|---|---|---|
| **M1** | Login/OTP · user management · verification queue · KYC document viewer · employees & permissions | **Backend** built and tested — the web **screens do not exist yet** (no web frontend has been built; S1 alert fires before building any M1 screen) |
| **M2** | Category tree · sub-category CRUD + attribute manager · takedown with reason | Rules fully written, screens not built |
| **M4** | All-conversations list · read-only chat viewer | Rules fully written, screens not built |
| **M5 itself** | Product monitoring list · dashboard · audit log viewer · Organisation list + detail | Planned in this document |

**14 screens in month 1.** Two more exist on paper but are out of month-1 scope — see §9.

## 3. Screen architecture

The console is one shell with a permission-filtered sidebar. There is no separate employee panel in month 1 — an employee logs into this same console and sees only the sections their permissions allow. The sidebar must render correctly with zero, one or many items.

```
Admin Console
│
├── Dashboard                          ← §5
│
├── Organisations                      ← §7
│     ├── list  (5 columns, filters)
│     └── detail
│           ├── header + block/unblock
│           ├── company details
│           ├── verification
│           ├── sides + claim history
│           ├── users
│           ├── buyer account chats     (only if buyer side)
│           ├── exporter account chats  (only if exporter side)
│           ├── products               (only if exporter side)
│           └── audit trail
│
├── Users
│     ├── list + prefix search
│     └── activate / deactivate
│
├── Verification
│     ├── queue
│     └── KYC document viewer          (permission: kyc:view)
│
├── Catalogue
│     ├── category tree                (top: toggle only)
│     ├── sub-category CRUD + attributes
│     └── product monitoring           ← §4
│
├── Conversations
│     ├── all conversations (search)
│     └── chat viewer (read-only)
│
├── Employees & permissions            (superadmin only)
│
└── Audit log                          ← §6
```

**Two navigation rules:**

Every count and badge in this console is a link. A number that cannot be clicked through to the list it counts is a dead end — the admin ends up re-finding the same rows by hand.

Cross-links between sections are expected and intentional: a product row reaches its seller's Organisation, its chats, and its public page. An Organisation reaches its products and its chats. These are the paths an actual investigation follows.

## 4. Product monitoring list

Read-only monitoring with one destructive-ish action. The admin **cannot edit a product** — under B6 the product belongs to the seller.

**Filters:** category · sub-category · status · seller · product name search

**Status filter has exactly three options:**

| Option | Reads |
|---|---|
| Active | `status: 'active'` |
| Inactive | `status: 'inactive'` — seller hid it |
| Blocked | `takedown.isDown: true` — admin action |

**Blocked deliberately reads the takedown object, not `status`.** An earlier attempt to treat `inactive` as the block was rejected: `status` is the seller's own field, so merging them would let a seller unblock themselves, would lose the prior state on unblock, and would break M4's chat labels which distinguish a seller hiding a product from an admin taking it down.

**Not shown at all:** `draft` products, and seller-`archived` products.

**Columns:** product name · seller company · category · status · takedown count for that seller · purge countdown · created date

Two of those need explaining:

- **Purge countdown.** A blocked product is deleted automatically after 180 days. Without a visible countdown the purge happens silently and the admin discovers it only when the row is gone.
- **The seller's cumulative takedown count.** Under A10 a taken-down product no longer occupies a slot in the D1 three-active cap, which means blocking a product *frees* a slot. Suspension of the account is therefore the only real abuse control left — and this column is the only place an admin would notice a repeat offender at all. Without it, that control has no trigger. **Source (§A24, 2026-07-30): the persisted `Organisation.takedownCount`** — increment-only, so it survives the 180-day purge; never counted from `Product` rows.

**Actions:** takedown (reason required) · restore · open product detail · view that product's chats · open the seller's public profile · open the seller's Organisation

The seller's **public profile** and the admin **Organisation detail** are two different destinations and both are needed.

**No bulk takedown.** If that many of a seller's products are wrong, the Organisation itself gets blocked. This is why the block action on the Organisation screen is prominent — it is the answer to "many bad products".

**Accepted gap:** hiding archived products means an admin can never see them again, even though their data is retained. A later "this seller listed it then deleted it" dispute has nothing to show. A link from the audit log could cover it later.

## 5. Dashboard

Three bands, ordered by how often they are acted on. Not a metrics wall — only things that ask for work.

**Needs action** (largest, at the top)
- Pending verifications — **buyer and exporter counted separately**, because they are different queues with different permissions. ⚠️ `kycStatus` is one shared value per Organisation, so a **both-sides** org in `submitted` appears in **both** queues and counts in **both** tiles — and whichever review happens first verifies the whole company (Decision 2, accepted). The tiles must not read as two independent reviews
- Rejected, awaiting resubmit
- Blocked products
- Nearing purge — blocked 150+ days

**Health** (a thin strip)
- Verification turnaround — average days from submission to decision. Computable today: `kycSubmittedAt` and `verifiedAt` both exist

**Totals** (smallest, at the bottom)
- Organisations by side (buyer / exporter / both) · active products · conversations · users

**Every number clicks through to the same list already filtered.** Tiles are permission-filtered the way the sidebar is — an employee holding only `exporter:verify` has no reason to see the buyer queue.

**Deliberately not on the dashboard:** saved-item counts, message counts, trend graphs. Month 1 will not have enough data for a graph to mean anything, and the quote explicitly puts detailed trend charts in a later phase.

## 6. Audit log viewer

A list, with the full entry shown on opening a row.

| List | Detail |
|---|---|
| Timestamp · actor · action · target | The whole entry — before/after snapshot, reason, actor role, target id |

**Filters:** actor · action type · date range · target

**Read-only and append-only.** No edit, no delete, no exceptions. This is the record that protects the operator in a dispute; a mutable audit log is worth nothing.

Action types it must cover, all of which already write entries or are specified to: KYC submit, KYC view, buyer approve/reject, exporter verify/reject, product takedown/restore, the 180-day purge, chat block/unblock, admin and employee chat reads, user activate/deactivate, employee permission changes, organisation block/unblock, and the organisation claim.

## 7. Organisation list and detail

New in importance because of A21: an Organisation can now hold a buyer side, an exporter side, or both, so the company — not the user — is the unit an admin governs.

### List — five columns only

| Column | Content |
|---|---|
| Company | Organisation name |
| Verification | Pending / Verified / Rejected |
| Products | Count |
| Takedowns | Count |
| State | Active / Blocked |

**Kept to five deliberately.** A wide table breaks on responsive; country and the sides badge move to the detail screen. Filters do not add width, so they stay: side · verification · blocked, sorted by takedown count.

Consider a second line under the company name for country or slug — company names collide, and two "Global Exports" rows are indistinguishable otherwise.

### Detail

Opening an Organisation shows **both sides' sections when the company has both**, and only the side that exists otherwise.

**Always shown**
- **Header** — name · slug · sides badge · verified state and since · active/blocked · block/unblock action
- **Company** — country · address · entityType · logo · description · created date
- **Verification** — status · who verified · when · rejection reason · link to KYC documents (`kyc:view`) · resubmit count · **which side was actually reviewed** — ⚠️ no field stores this: **derive it from the AuditLog rows** (`buyer.approve` vs `exporter.verify`); do not add a schema field for it (rule 14)
- **Sides** — which sides are enabled and when · **claim history**: who claimed which side, when. ⚠️ `buyerSide`/`exporterSide` are plain booleans with no timestamp — the "when" and the claim history are **derived from AuditLog** (signup + `org.claim` rows, once A21 Step 4b writes them); no schema field
- **Users** — every user on this Organisation, role, active/blocked, last login — reads **`User.lastLoginAt`**, which **already exists and is set on every successful login** (verified in code, 2026-07-30). Not derived from AuditLog (too expensive per row)
- **Audit trail** — this Organisation's full record
- **Buyer account chats** — count and link, if the buyer side exists
- **Exporter account chats** — count and link, if the exporter side exists

**Exporter side only**
- Products by status (active / inactive / archived / blocked) · takedown count and history · link to the monitoring list filtered to this Organisation · link to the public seller profile
  - *(🚫 "working categories" was listed here — **cancelled 2026-07-30** along with "business type"; the field does not exist and will not be built. `entityType` covers the purpose.)*

**Buyer side only**
- Enquiries sent · saved items · link to conversations

**Why two chat sections rather than one list:** `Conversation` stores organisation ids — `buyerOrgId` and `exporterOrgId` — not user ids. Only `Message.senderUserId` holds a person. Since both fields are distinct, one Organisation holding both sides still produces two clean lists, each filtering on its own field.

### Three things this screen must be honest about

**1. Blocking does less than it appears to.** F1 in the FINALIZE module specifies that a block cascades to the organisation's catalogue, products and chats. That is not built. Today a block acts on the Organisation and its users only. The screen must show what actually happens, or an admin will block a company, assume its listings are hidden, and leave them live.

**2. `kycStatus` is one shared value across both sides.** Whichever side is reviewed first verifies the whole Organisation, so a buyer-approved company that later claims an exporter side inherits the public verified tick with no exporter-side review. This was accepted knowingly. The screen should therefore show **which side was actually reviewed**, otherwise an unreviewed exporter side looks verified.

**3. Some fields will always be empty.** `registrationNumber`, `website`, `taxId`, `establishedYear` and `authorisedSignatory` exist on the model but no form captures them — identity capture moved to Phase 2. Either hide them or label them "not captured", but do not render permanently blank fields as if they were awaiting input.

## 8. Employees in this console

There is no separate employee panel in month 1. An employee logs into this console and the sidebar filters to their permissions.

This is not a compromise — M1 already grants employees `buyer:approve`, `exporter:verify` and `kyc:view`, and already built a permission-driven sidebar. Building a second surface would leave those permissions unusable.

The employee panel of the quote's Module 6 — its own dashboard, ticket queue, internal notes, seller directory and reports — is month 2.

**New permissions this module needs.** M1 grants four (`buyer:approve`, `exporter:verify`, `user:read`, `kyc:view`); **M2 adds four more, decided 2026-07-31 (§A25): `category:read`, `category:manage`, `product:read`, `product:takedown`** — catalogue writes are grantable by owner decision (supersedes the 07-30 superadmin-only default). Governance stays hard-gated (`requireRole('superadmin')`, never grantable). Still to propose before building: the **conversation** (M4) and **organisation** (M5) screen read permissions — do not invent permission strings inline.

## 11. Rules carried in from other modules

These are not M5's to change. They are listed because M5 is where they become visible.

- **B6** — no approval workflow on products. The seller owns `status`. Admin can take down; admin never hard-deletes
- **B7** — verification never filters public results. Public seller reads return a `verified` boolean and `verifiedAt`, never raw `kycStatus`
- **D1** — unverified exporters capped at 3 active products, and taken-down products are excluded from that count
- **A8** — a product blocked more than 180 days has its row and images deleted, with an AuditLog entry snapshotting the product and seller names
- **Category cascade** — deactivating a top category stores each sub's `prevActive` first, so reactivating restores rather than blanket-enabling
- **Top categories** — activate/deactivate only. Image upload is a deliberate, narrow exception (A20)
- **M4 chat** — admin is present in every conversation but read-only; the viewer has no composer and the server rejects admin sends by role
- **No `admin` role** — four roles only. Everywhere this document says "admin" it means superadmin, or an employee holding the relevant permission
