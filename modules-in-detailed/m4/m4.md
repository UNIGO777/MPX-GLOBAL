# MPX — Module 4: Enquiry & Chat

**Status:** planned and locked. Not built. No code exists.
**Depends on:** M2 (Product, Category) and M3 (public seller profile) must exist first.
**Precedence:** where this document contradicts an older plan doc, this document wins.

---

## 1. What this module is

The only channel through which a buyer and a seller can reach each other. Contact details are hidden everywhere else on the platform by design, so every conversation on MPX starts here and stays here.

**In scope:** enquiry creation, the chat thread, read/unread, the chat list with search, admin visibility, admin chat block, and the effects of product and account state changes on a thread.

**Out of scope:** quotations and negotiation (separate deferred module), attachments, notifications, voice or video, typing indicators, online status, and any admin participation in a conversation.

---

## 2. Core concepts

**A conversation is a group room.** Three parties are present: the buyer, the seller, and the platform. Buyer and seller do the talking. The platform is present but silent after its opening message.

This is deliberate. The platform can see every conversation — putting it visibly in the room from the first message makes that disclosure rather than surveillance. Both sides know.

**A thread belongs to a product.** Every conversation is anchored to exactly one product, and a buyer has exactly one thread per product. There is no such thing as a product-less conversation, and a second enquiry never opens a second thread.

**Enquiry and conversation are created together.** They are always one-to-one, but they stay separate models: `Inquiry` holds the structured commercial ask, `Conversation` holds the messaging. Phase 2's quotation module will attach to `Inquiry`.

## 3. Decisions

### Structure

| # | Decision |
|---|---|
| **M4-1** | Every conversation is a group room — buyer, seller, platform. The platform's presence stays visible in the thread header or participant list, not just in the opening message |
| **M4-2** | B1 scoping holds: `parties: [buyerOrgId, exporterOrgId]`, indexed. Admin access comes from role, never from membership — the platform is never added to `parties` |
| **M4-3** | One thread per (buyer org + product). Enforced by a unique index, not just by UI |
| **M4-4** | No product-less enquiries. A supplier's profile lists their products; the buyer enquires from one of them |
| **M4-5** | One enquiry per product, unlimited messages afterwards. This is the spam control — there is no separate message quota |
| **M4-6** | `Inquiry` is not merged into `Conversation`. It carries real commercial data and is what Phase 2 attaches to |

### The enquiry itself

| # | Decision |
|---|---|
| **M4-7** | The enquiry is a structured **form**, not a free-text box: fixed fields plus a note |
| **M4-8** | The structured data is stored on `Inquiry`, so it stays queryable. The thread's first message is **composed** from those fields plus the note — stored once, rendered for chat |
| **M4-9** | The field set differs for goods and services and follows the sub-category's `type`, exactly as the product form does. Exact fields are a build-time detail |
| **M4-10** | Message order in a new thread is fixed: the buyer's enquiry is the **first** message, the automated platform welcome is the **second** |
| **M4-11** | The welcome message is an automated system template. No human types it. One template; only names change, or it runs with no names |

### Messaging

| # | Decision |
|---|---|
| **M4-12** | Message body limit is **200 characters** — for **normal user messages only**. The composed **first enquiry message** (structured fields + note, M4-8/M4-10) and **system messages** are **exempt** (decided 2026-07-30: the composed first message will routinely exceed 200, and a model-level cap would reject the thread's own opening). Only the note is free text — structured enquiry fields are separate and unaffected |
| **M4-13** | Sent messages can never be edited or deleted, by anyone |
| **M4-14** | **No attachments** in month 1. Document exchange waits for the Quotation module |
| **M4-15** | Detecting contact details shared inside chat is **Phase 2**. Nothing in Phase 1 |
| **M4-16** | Messages are never all loaded at once. Opening a thread loads the current window; scrolling up fetches earlier messages in bundles |

### Titles and display

| # | Decision |
|---|---|
| **M4-17** | Thread title depends on who is looking: seller sees *product × buyer company*, buyer sees *product × seller company*, admin sees *buyer × seller × product*. **Company names, never person names** |
| **M4-18** | Nothing is stored as a "title". It is composed at read time — the product name from the live product while it exists, from the snapshot after it is purged |
| **M4-19** | Colour never carries meaning alone. Every label pairs a colour with text |

### Product state and its effect on a thread

| # | Decision |
|---|---|
| **M4-20** | Seller sets the product inactive or archives (deletes) it → **the chat is unaffected**. Messaging continues, no label |
| **M4-21** | Admin takes the product down → messaging **freezes on both sides immediately**, a system message explains there is an issue and suggests other suppliers, and a **yellow** label appears in the chat list. The takedown is still reversible at this point |
| **M4-22** | The product is purged at 180 days → the chat is **untouched**, stays frozen with full history, and the label turns **red**. This only works because the product name was snapshotted into `Conversation` at creation |

### Enforcement

| # | Decision |
|---|---|
| **M4-23** | Admin can block a **single chat**, independently of the product. Messaging freezes both sides, a system message is posted, a red label appears, and an AuditLog entry is written. The product stays live and its other chats are unaffected |
| **M4-24** | A chat block is **reversible**, and **admin** performs it |
| **M4-25** | **Both parties** see the reason the admin wrote |
| **M4-26** | Exactly **two enforcement levels** exist: block a single chat, or suspend the whole account. A middle "stop this buyer contacting this seller entirely" level was considered and rejected |
| **M4-27** | **Accepted gap:** a blocked buyer can still open a new chat on a different product. Repeat behaviour is handled by suspending the account |
| **M4-28** | When a buyer's account is blocked, the seller is shown that the buyer is blocked, and those chats freeze the same way a seller-block freezes them |
| **M4-29** | **First reason wins.** `frozenReason` is set once and never overwritten — if a chat was blocked and the product is taken down afterwards, the label stays on the chat block |
| **M4-30** | Because reasons can stack, unfreezing is **not** a simple toggle. Every unfreeze must check whether another reason still applies before the thread reopens |
| **M4-39** | **Self-enquiry guard (F4 — built HERE, in M4, decided 2026-07-30).** Enquiry creation rejects when the buyer account's org is the product's own `exporterOrgId` (`buyerOrgId === exporterOrgId` — possible since A21 lets one Organisation hold both sides). Without it the same thread shows in both portals, the company notifies itself, and enquiry counts skew. Server-side check at `POST /inquiries`, not a UI hide |

### List and search

| # | Decision |
|---|---|
| **M4-31** | The chat list has no size limit and no archiving. It never "fills up" |
| **M4-32** | Search covers the conversation **list only**. Message content is never searched |
| **M4-33** | Search matches three names and two ids. Role changes only the scope filter, never the searched fields |
| **M4-34** | Employees may be granted read access to conversations, but **their reads are audited** exactly as a superadmin's are |

### Surfaces

| # | Decision |
|---|---|
| **M4-35** | OLX-style: filling the enquiry form drops the buyer straight into the thread. There is no enquiry inbox — one role-aware chat list serves everyone |
| **M4-36** | Web and mobile behave identically for buyer and seller |
| **M4-37** | Mobile gets a WhatsApp-style chat list, without archive-type features |
| **M4-38** | In month 1 employees get **read permission only**. The employee panel itself is month 2 |

### Conversation

The thread. One-to-one with Inquiry.

| Field | Notes |
|---|---|
| `inquiryId` | ref Inquiry |
| `parties` | `[buyerOrgId, exporterOrgId]`, indexed — the B1 scoping field |
| `buyerOrgId`, `exporterOrgId` | explicit, for scoped queries and id search |

| `lastMessageAt` | list ordering |
| `lastMessagePreview` | list rendering without fetching messages |
| `buyerLastReadAt`, `exporterLastReadAt` | unread is derived from these |
| `createdAt` | |

## 6. Flows

### 6.1 Enquiry to live chat

```
Buyer on product page — button reads "Create enquiry"
        ↓
Buyer fills the enquiry form
        ↓
Inquiry created  +  Conversation created
        ↓
First message written  — composed from the form + note, senderType: buyer
        ↓
Second message written — automated welcome, senderType: system
        ↓
Buyer lands in the chat thread
        ↓
Revisiting the product later — button now reads "Open chat"
```

### 6.2 Sending a message

```
Sender types and sends
        ↓
Server checks: is this org a party? is the thread frozen? is the body within 200?
        ↓
Message saved · Conversation updated (lastMessageAt, lastMessagePreview)
        ↓
Broadcast to the conversation room
        ↓
Other members with the thread open see it live; others see it on next load
```

### 6.3 Admin takes the product down

```
Admin takedown
        ↓
Messaging frozen both sides · system message posted · yellow label
        ↓
   ┌────────────────────────┴────────────────────────┐
Admin restores                              No action for 180 days
   ↓                                                  ↓
Messaging resumes, label clears              Product row + images deleted
                                             AuditLog keeps the snapshot
                                                      ↓
                                             Red label, chat stays frozen,
                                             full history readable
```

### 6.4 Admin blocks one chat

```
Admin sees a problem in a thread
        ↓
Blocks that chat, with a reason
        ↓
Messaging frozen both sides · system message · red label · AuditLog entry
        ↓
Product stays live, its other chats unaffected
Buyer can still open a chat on another product — accepted gap
        ↓
If behaviour repeats → the whole account is suspended
```

### 6.5 Account block cascade

Owned by the FINALIZE module (entry F1), not built here. When an account is blocked, every conversation involving that org freezes with the same reason. Before freezing, each thread's prior state must be stored so that unblocking restores it rather than blanket-reopening threads that were already frozen for their own reasons.

## 7. Real-time architecture

### 7.1 The split

Only live delivery goes over the socket. Everything else is ordinary REST.

| REST | Socket |
|---|---|
| create enquiry · fetch chat list · fetch message history · mark read · admin block and unblock | deliver new messages · announce freeze and unfreeze |

If the socket drops, the application still works — it just stops updating live.

### 7.2 Connection and rooms

The socket authenticates with the same JWT as REST, and checks `tokenVersion` — so a blocked user is disconnected immediately rather than at next page load.

⚠️ Build note: a handshake-time check alone does **not** deliver "immediately" — an already-open
socket keeps working after a `tokenVersion` bump. Either re-verify the token on every
`message:send` (cheap — the send guard already hits the DB for freeze/party checks) or emit a
force-disconnect to the user's sockets when `tokenVersion` changes. Pick one at build time; do not
rely on the handshake alone.

| Who | Rooms |
|---|---|
| Buyer, seller | joined to all their conversation rooms on connect |
| Admin | joined to **no** rooms by default; joins a single room, read-only, when a thread is opened |

Admin is deliberately not in every room — there will be thousands of threads and no reason to push all of them at an idle admin.

### 7.3 Server-side guards

The client disabling a control is never the enforcement. All three of these are checked server-side on every send:

- the sender's org is a party to the thread
- the thread is not frozen
- the body is within 200 characters *(normal user sends; the composed first message and system messages are exempt — M4-12)*

Admin sends are rejected by role. Admin can read; admin cannot speak.

### 7.4 Freeze is pushed, not polled

When an admin takes a product down or blocks a chat, the server sets the state and emits to the room. Both composers disable immediately — no refresh, no polling.

### 7.5 Unread

No counters are maintained. Unread is derived by comparing `buyerLastReadAt` / `exporterLastReadAt` against message timestamps. Opening a thread updates the reader's timestamp.

### 7.6 Pagination

Cursor-based, never page numbers. "Give me the 30 messages before this one." Page numbers break when a new message arrives mid-scroll — rows shift, and the reader sees a duplicate or a gap. The `(conversationId, createdAt)` index serves this directly.

### 7.7 Scaling note

Socket.io works in-memory within one server process. The moment hosting runs more than one process, a **Redis adapter** becomes mandatory — otherwise a message sent through one process never reaches a user connected to another. Redis is already on the client dependency list; this module makes it non-optional.

## 8. Chat list search architecture

### 8.1 What is searched

The conversation list only. Never message content.

| Matched on | Type |
|---|---|
| `productNameSnapshot` | name |
| `buyerOrgName` | name |
| `exporterOrgName` | name |
| `buyerOrgId` | id — paste an id directly |
| `exporterOrgId` | id |

### 8.2 Why the company names are denormalised

Today `Conversation` carries only the product name. Company names live on `Organisation`.

Without denormalising, searching by company name means: query Organisation for matching names, collect the org ids, then query Conversation for those ids. Two round trips, and pagination becomes unreliable across them.

Storing `buyerOrgName` and `exporterOrgName` on `Conversation` at creation makes it one query with no join.

This matters for every role, not only admin — each role's list title shows the counterparty's company name, so that is exactly what people will type. The performance argument is admin-specific; the correctness argument applies to everyone.

### 8.3 Engine

Atlas Search, already locked for M3 and already in the stack. An index over the three name fields provides typo tolerance and partial matching without extra work.

### 8.4 One query, one filter

Roles differ **only** in scope. The searched fields are identical for everyone.

```
search(text, role, myOrgId):

  scope filter:
    buyer   → { buyerOrgId: myOrgId }
    seller  → { exporterOrgId: myOrgId }
    admin   → { }

  match against:
    productNameSnapshot, buyerOrgName, exporterOrgName
    buyerOrgId, exporterOrgId              (when the input looks like an id)

  sort:      lastMessageAt descending
  paginate:  cursor
```

Three separate code paths would eventually diverge, and the one that diverges is the one that leaks. One path, one filter.

### 8.5 Renames

When an Organisation changes its name, the denormalised copies on its conversations must be updated. Renames are rare; the update is cheap.

Mobile carries screens 2 and 3 in WhatsApp-style form. Admin screens are web only.

### States to draw

Loading, empty, error and success for each. The three most often missed:

- **empty chat list** — no enquiries yet
- **frozen thread** — composer disabled, label visible, system message in place
- **purged product thread** — red label, and no link to a product page that no longer exists

## 12. Rules carried in from elsewhere

- **B1** — two-party scoping on all three models
- **F4 self-enquiry guard** — built in this module at enquiry creation (M4-39), not left to FINALIZE
- **Contact details are never exchanged.** The thread is the only channel; this is the reason the module exists
- **Whitelist projections** — anything this module exposes goes through `toPublic()`
- **AuditLog** — chat block, unblock, and every admin or employee read of a conversation
- **Product name snapshot** — the carry-forward from the product purge decision; without it, purged threads lose their identity
